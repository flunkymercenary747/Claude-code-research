# Глава 12: Терминальный UI и движок рендеринга

## 12.1 Обзор и позиционирование

Claude Code — интерактивный AI-ассистент для программирования, работающий в терминале. Его UI-слой должен обеспечивать близкий к GUI интерактивный опыт в среде текстового терминала: потоковый рендеринг сообщений, редактирование в стиле Vim, выделение текста мышью, подсветку поиска, многоуровневые наложения окон. Эти требования выходят далеко за пределы возможностей традиционных CLI-инструментов.

UI-слой терминала Claude Code строится на трёх ключевых архитектурных решениях:

1. **Кастомный рендерер Ink** (`src/ink/`): глубокая переработка фреймворка React + Ink с введением модели двойного буфера экрана, движка ANSI diff, аппаратного ускорения прокрутки и IME-чувствительного позиционирования физического курсора.
2. **Декларативное дерево компонентов** (`src/screens/REPL.tsx`, `src/components/`): описание структуры UI через компоненты React; движок рендеринга транслирует виртуальный DOM в матрицу символов терминала.
3. **Полноценный режим Vim** (`src/vim/`): независимая реализация конечного автомата, охватывающая оба режима NORMAL/INSERT, полный набор operators/motions/textObjects, а также dot-repeat и регистры.

Ритм всего конвейера рендеринга задаётся константой `FRAME_INTERVAL_MS = 16` (`src/ink/constants.ts:1`), теоретическая частота кадров — 62,5 fps, что согласуется с частотой обновления монитора.

## 12.2 Теоретические основы

### Принципы рендеринга в терминале

Рендеринг в терминале по существу сводится к записи потока байт в файловый дескриптор; терминальный эмулятор разбирает их и обновляет экран. Ключевые механизмы:

- **ANSI escape codes**: управляющие последовательности с префиксом `\x1b[`, задающие позицию курсора (CSI CUP), цвет (SGR), область прокрутки (DECSTBM), отслеживание мыши (DEC private modes) и др. Директория `src/ink/termio/` в Claude Code инкапсулирует эти последовательности в именованные константы (`CURSOR_HOME`, `ENTER_ALT_SCREEN`, `ENABLE_MOUSE_TRACKING` и т.д.).
- **termios / raw mode**: в режиме raw каждое нажатие клавиши немедленно передаётся программе без построчной буферизации и эха. Claude Code при запуске захватывает stdin через `setRawMode(true)` и восстанавливает его при завершении в `Ink.detachForShutdown()` (`ink.tsx:942-950`).
- **Alt Screen (?1049h/?1049l)**: альтернативный буфер экрана — вход в него не загрязняет историю прокрутки основного экрана, выход восстанавливает исходное состояние. В полноэкранном режиме (`isFullscreenEnvEnabled()`) REPL оборачивается в компонент `<AlternateScreen>`.

### Двойная буферизация

Claude Code использует два буфера кадра (`frontFrame` / `backFrame`) для двойной буферизации (`ink.tsx:196-197`):

```typescript
// ink.tsx:196-197
this.frontFrame = emptyFrame(this.terminalRows, this.terminalColumns, this.stylePool, this.charPool, this.hyperlinkPool);
this.backFrame  = emptyFrame(this.terminalRows, this.terminalColumns, this.stylePool, this.charPool, this.hyperlinkPool);
```

При рендеринге каждого кадра:
1. Renderer записывает виртуальный DOM React в `backFrame` (новый кадр)
2. Движок diff LogUpdate сравнивает `frontFrame` (старый кадр) с `backFrame` и генерирует минимальную последовательность patch
3. Последовательность patch записывается в терминал, `frontFrame` ↔ `backFrame` меняются местами (`ink.tsx:594`)

Таким образом, терминал получает только реально изменившиеся символы, а не полную перерисовку каждого кадра.

### Применение React в среде без DOM (Custom Renderer)

Интерфейс рендерера React (`react-reconciler`) допускает произвольную хостовую среду. Claude Code реализует Custom Renderer для терминала в `src/ink/reconciler.ts` (512 строк):

- Тип хостового элемента — пользовательский `dom.DOMElement` (`src/ink/dom.ts`)
- Движок компоновки использует Yoga (реализация Flexbox от Facebook), управляемый в callback `onComputeLayout` (`ink.tsx:239-258`)
- Режим React Concurrent Root (`ConcurrentRoot`) допускает прерывание рендеринга, предотвращая длительную блокировку главного потока

## 12.3 Кастомный рендерер Ink

### Кастомные доработки Ink в Claude Code

`src/ink/ink.tsx` (1 722 строки) — ключевой контроллер всего UI-слоя, определяет класс `Ink`. Это не оригинальный пакет Ink, а глубоко переработанная кастомная версия; ключевые улучшения:

**Двойной буфер + управление передним/задним кадрами**: оригинальный Ink выводит строки напрямую, кастомная версия вводит объекты кадра (`Frame`) и матрицу `Screen`.

**Мониторинг производительности**: каждый кадр фиксирует время выполнения фаз renderer, diff, optimize, write, а также метрики компоновки Yoga: visited/measured/cacheHits; экспортируется через callback `onFrame` (`ink.tsx:772-788`):

```typescript
// ink.tsx:772-788
this.options.onFrame?.({
  durationMs: performance.now() - renderStart,
  phases: {
    renderer: rendererMs,
    diff: diffMs,
    optimize: optimizeMs,
    write: writeMs,
    patches: diff.length,
    yoga: yogaMs,
    commit: commitMs,
    yogaVisited: yc.visited,
    yogaMeasured: yc.measured,
    yogaCacheHits: yc.cacheHits,
    yogaLive: yc.live,
  },
  flickers,
});
```

**Передача управления внешнему TUI**: методы `enterAlternateScreen()` / `exitAlternateScreen()` приостанавливают управление Ink и отключают протокол kitty keyboard, позволяя внешним редакторам (vim, nano) работать нормально, и полностью восстанавливают состояние при возврате (`ink.tsx:357-419`).

**Самовосстановление при SIGCONT**: `handleResume` обрабатывает восстановление процесса из приостановки (команда fg): главный экран сбрасывает буферы, альтернативный экран повторно входит и очищается (`ink.tsx:280-301`).

### Двойной буфер + механизм diff-обновления

`LogUpdate.render()` в `src/ink/log-update.ts` — ядро движка diff. Принимает `prev: Frame` и `next: Frame`, возвращает набор операций `Diff` patch:

```
Типы Diff patch:
- { type: 'stdout', content: string }    — прямая запись в терминал
- { type: 'cursorMove', x, y }           — относительное перемещение курсора
- { type: 'cursorTo', x, y }             — абсолютное позиционирование курсора
- { type: 'styleStr', str }              — переключение стиля SGR
- { type: 'hyperlink', uri }             — гиперссылка OSC 8
- { type: 'cursorHide' | 'cursorShow' }  — видимость курсора
- { type: 'clear', count }               — стирание символов
- { type: 'clearTerminal', reason }      — полная перерисовка (вызывает мерцание)
```

Движок diff проходит через однопроходный оптимизатор в `src/ink/optimizer.ts` (`optimize(diff)`): объединяет соседние `cursorMove`, сворачивает последовательные `cursorTo`, склеивает соседние `styleStr`, отменяет пары cursor hide/show — уменьшая фактический объём записи.

### Буфер экрана на Int32Array

`src/ink/screen.ts` определяет тип `Screen`, использующий `Int32Array` вместо массивов объектов для хранения ячеек экрана, устраняя давление на GC (`screen.ts:356-370`):

```typescript
// screen.ts:356-370（注释）
// Screen uses a packed Int32Array instead of Cell objects to eliminate GC
// pressure. For a 200x120 screen, this avoids allocating 24,000 objects.
//
// Cell data is stored as 2 Int32s per cell in a single contiguous array:
//   word0: charId (full 32 bits — index into CharPool)
//   word1: styleId[31:17] | hyperlinkId[16:2] | width[1:0]
```

`createScreen` выделяет `ArrayBuffer` и монтирует к нему два представления (`Int32Array` и `BigInt64Array`), последнее используется для пакетного обнуления в `resetScreen` (`screen.ts:472-490`):

```typescript
// screen.ts:472-490
const buf = new ArrayBuffer(size << 3) // 8 bytes per cell
const cells = new Int32Array(buf)
const cells64 = new BigInt64Array(buf)
```

Символы и стили интернируются через **разделяемые объекты Pool** (`CharPool`, `StylePool`, `HyperlinkPool`): ID разделяются между Screen, что позволяет `blitRegion` напрямую копировать целочисленные ID без повторного интернирования, а `diffEach` использовать сравнение целых чисел вместо строк (`screen.ts:17-31`).

Бит 0 при интернировании `StylePool.intern()` кодирует видимость (`screen.ts:148-161`): нечётный ID означает, что данный стиль виден для пробела (цвет фона, обратный цвет, подчёркивание), позволяя рендереру пропускать невидимые пробелы одной битовой маскировкой без лишних записей.

### Аппаратная прокрутка (DECSTBM)

В `log-update.ts` реализована оптимизация аппаратной прокрутки DECSTBM (`log-update.ts:149-185`):

Когда в режиме alt-screen изменяется `scrollTop` компонента `ScrollBox`, вместо перезаписи всей области прокрутки отправляется `CSI top;bot r` (установка области прокрутки) + `CSI n S` (прокрутка вверх на n строк); аппаратное ускорение терминала выполняет смещение содержимого, требуя заполнить только новые строки. Параллельно выполняется `shiftRows()` над `prev.screen` для имитации прокрутки, позволяя последующему циклу diff естественно находить изменённые строки вместо полной перезаписи.

Оптимизация включается только при `decstbmSafe=true` — когда внешний терминал не поддерживает DEC 2026 (атомарные операции BSU/ESU), tmux и аналогичные терминалы могут отображать промежуточное состояние (между прокруткой и заполнением строк), вызывая видимое мерцание; в этом случае происходит откат к полному diff (`log-update.ts:158-167`).

### Кеш на 16 384 символа

Класс `Output` в `src/ink/output.ts` (внутренний движок измерения символов и вывода рендерера) поддерживает `charCache` — кеш отображения символов в их измеренную ширину. При превышении 16 384 записей кеш полностью очищается и перестраивается (`output.ts:204`):

```typescript
// output.ts:204
if (this.charCache.size > 16384) this.charCache.clear()
```

Аналогично, `src/ink/line-width-cache.ts` поддерживает кеш ширины строк (максимум 4096 записей) для переиспользования вызовов `stringWidth` большого числа неизменившихся строк при потоковом выводе (`line-width-cache.ts`):

```typescript
// line-width-cache.ts
// During streaming, text grows but completed lines are immutable.
// Caching stringWidth per-line avoids re-measuring hundreds of
// unchanged lines on every token (~50x reduction in stringWidth calls).
const MAX_CACHE_SIZE = 4096
```

### Поток рендеринга сообщений

Состояние сообщений хранится в React `useState<MessageType[]>` и обновляется через `handleMessageFromStream` при обработке потоковых SSE-событий (добавление/обновление сообщений). Список сообщений рендерится в компонент `<Messages>` или `<VirtualMessageList>`, последний использует виртуальную прокрутку и рендерит только видимую область, предотвращая создание большого количества DOM-узлов в длинных диалогах.

В REPL присутствует несколько оптимизаций для предотвращения излишних перерисовок: `AnimatedTerminalTitle` выделен в отдельный листовой узел, чтобы анимационные тики каждые 960 мс не вызывали перерисовку всего дерева REPL (в комментарии `REPL.tsx` указано: `Before extraction, the tick was ~1 REPL render/sec for the duration of every turn, dragging PromptInput and friends along`).

`useDeferredValue(searchQuery)` используется для откладывания вычислений поиска; `React.memo` кеширует поддерево `PromptInput`, предотвращая распространение частых перерисовок при вводе символов вверх по дереву.

### Конвейер обработки ввода

Пользовательский ввод поступает из stdin в режиме raw в `parse-keypress.ts` Ink, разбирается в объект `ParsedKey` и через FocusManager распределяется в callback `useInput` текущего узла с фокусом. `GlobalKeybindingHandlers` и `CommandKeybindingHandlers` предоставляют механизм регистрации глобальных горячих клавиш с приоритетом выше компонентного `useInput`.

Ввод в конечном счёте достигает компонента `PromptInput` и, в зависимости от текущего режима (Vim/Standard), направляется в `VimTextInput` или `TextInput`.

## 12.5 Режим Vim

### Архитектура реализации режима Vim

Директория `src/vim/` (5 файлов, ~1 513 строк) реализует полноценный слой Vim-клавиш. Архитектурный замысел предельно лаконичен: **типы как документация** — все переходы конечного автомата закодированы в TypeScript-типах, исчерпывающая проверка TypeScript гарантирует полноту обработки состояний.

Распределение файлов:
- `types.ts`: определения типов конечного автомата + наборы констант
- `transitions.ts`: функции переходов (главная точка входа `transition()`)
- `motions.ts`: чистые функции перемещения курсора (`resolveMotion()`)
- `operators.ts`: функции выполнения операций (delete/change/yank и др.)
- `textObjects.ts`: вычисление границ текстовых объектов

### Поддерживаемые операции (motions, operators, textObjects)

**Operators (операторы)**: `d` (delete), `c` (change), `y` (yank) — определены в `types.ts:OPERATORS`.

**Simple Motions** (`types.ts:SIMPLE_MOTIONS`):
- Базовое перемещение: `h`/`l`/`j`/`k`
- Перемещение по словам: `w`/`b`/`e`/`W`/`B`/`E`
- Позиция в строке: `0`/`^`/`$`

**Find Motions**: `f`/`F`/`t`/`T` (поиск символа), `;`/`,` повтор/реверс.

**Text Objects** (`types.ts:TEXT_OBJ_TYPES`): `w`/`W` (слово), `"`/`'`/`` ` `` (кавычки), `(`/`)`/`b` (скобки), `[`/`]` (квадратные скобки), `{`/`}`/`B` (фигурные скобки), `<`/`>` (угловые скобки).

**Построчные операции**: `dd`/`cc`/`yy`, `D`/`C`/`Y`, `o`/`O` (открыть строку), `J` (join), `>>`/`<<` (отступ).

**Прочие команды**: `r` (replace char), `~` (toggle case), `x` (delete char), `p`/`P` (paste), `u` (undo), `G`/`gg` (переход к строке), `.` (dot-repeat).

Специальная обработка: `cw`/`cW` изменяет до конца слова, а не до начала следующего (классическое поведение vim, `operators.ts:91-102`); Image ref chip распознаётся как атомарная единица, перемещение по словам не останавливается внутри chip (`operators.ts:333-337`).

### Конечный автомат и переключение режимов

`VimState` — тип верхнего уровня (`types.ts:52-55`):

```typescript
// types.ts:52-55
export type VimState =
  | { mode: 'INSERT'; insertedText: string }
  | { mode: 'NORMAL'; command: CommandState }
```

Режим INSERT записывает введённый текст для dot-repeat; режим NORMAL хранит подсостояние `CommandState`.

`CommandState` имеет 11 состояний (`types.ts:62-75`): idle, накопление счётчика, ожидание оператора, operatorCount, operatorFind, operatorTextObj, find, префикс g, operatorG, replace, indent. Граф состояний документирован в начале `types.ts` в виде ASCII art (`types.ts:1-26`):

```
idle ──┬─[d/c/y]──► operator
       ├─[1-9]────► count
       ├─[fFtT]───► find
       ├─[g]──────► g
       ├─[r]──────► replace
       └─[><]─────► indent
```

Функция `transition()` (`transitions.ts:55-73`) диспетчеризует по типу текущего `CommandState` к специализированным обработчикам, каждый из которых возвращает `{ next?: CommandState; execute?: () => void }`. При наличии `execute` он выполняется немедленно, при наличии `next` состояние продвигается; если нет ни того, ни другого — возврат в idle.

`PersistentState` (`types.ts:80-87`) сохраняется между командами: `lastChange` (запись для dot-repeat), `lastFind` (повтор `;`/`,`), `register` (буфер обмена), `registerIsLinewise` (определение построчной вставки).

Умножение счётчиков реализовано в `fromOperatorCount` (`transitions.ts`): `effectiveCount = state.count * motionCount`, поддерживает `3d2w` = удалить 6 слов. Верхний предел счётчика — `MAX_VIM_COUNT = 10000` (`types.ts:96`), защищающий от вредоносного ввода.

## 12.6 Анализ ключевых компонентов

### Компонент ввода PromptInput

`src/components/PromptInput/PromptInput.tsx` (2 338 строк) — один из самых функционально насыщенных компонентов Claude Code, несущий почти всю логику взаимодействий, связанных с вводом.

**Масштаб Props**: определение типа `Props` занимает около 60 строк и включает значение ввода, режим, состояние Vim, стек stash, callback подтверждения, контекст разрешений, клиент MCP, выделение IDE, голосовую интеграцию и многое другое.

**Инъекция внешнего ввода**: `insertTextRef` предоставляет интерфейс `{ insert, setInputWithCursor, cursorOffset }`, позволяя голосовому распознаванию (STT) вставлять текст в позицию курсора без замены всего ввода (`PromptInput.tsx:180-200`).

**Управление курсором**: `cursorOffset` отслеживается как отдельное состояние, различая внутренние изменения (через `trackAndSetInput`, оборачивающий `onInputChange`) и внешние инъекции (голосовой ввод); внешние изменения перемещают курсор в конец (`PromptInput.tsx:164-176`).

**Маршрутизация режима**: в зависимости от `isVimModeEnabled()` рендерит `<VimTextInput>` или `<TextInput>`, оба разделяют интерфейс `BaseTextInputProps`.

**Константы нижнего макета** (`PromptInput.tsx`):
```typescript
const PROMPT_FOOTER_LINES = 5;
const MIN_INPUT_VIEWPORT_LINES = 3;
```
Максимальная высота нижнего слота ввода — 50%, резервируя 5 строк для footer, рамки и подсказок состояния.

### Интерфейс настроек

`src/components/Settings/Config.tsx` (1 821 строка) реализует интерфейс настроек команды `/config`.

**Навигация через поиск**: Config по умолчанию входит в режим поиска (`isSearchMode = true`), пользователь может сразу вводить текст для фильтрации элементов настроек без прокрутки списка стрелками. `maxVisible = Math.max(5, paneCap - 10)` динамически вычисляет количество видимых элементов в зависимости от высоты терминала.

**Категории настроек**: массив `settingsItems: Setting[]` единообразно определяет все параметры конфигурации; каждый элемент является одним из: `boolean` (переключатель), `enum` (выбор из вариантов) или `managedEnum` (управляется кастомным компонентом).

**Отслеживание изменений и откат**: состояние `changes` записывает все модификации; ref `isDirty` используется для определения при нажатии Escape — нужно ли записать откат на диск, чтобы избежать бессмысленных дисковых операций при открытии и закрытии без изменений (`Config.tsx`).

**Система подменю**: состояние `showSubmenu` управляет раскрытием подменю Theme, Model, TeammateModel, ExternalIncludes, OutputStyle, Language, EnableAutoUpdates и т.д.; через `setTabsHidden` сообщает родительскому компоненту Settings о скрытии заголовков вкладок.

**Архитектура многоисточниковой конфигурации**: источники настроек разделены на `localSettings` (уровень проекта) и `userSettings` (уровень пользователя), читаются/записываются через `getSettingsForSource`/`updateSettingsForSource`; при откате Escape используются начальные снимки на уровне каждого источника, а не объединённое глобальное представление (в комментарии `Config.tsx` объясняется, что это необходимо для поддержки семантики удаления ключей через `undefined`).

### Выбор логов

`src/components/LogSelector.tsx` (1 574 строки) реализует интерфейс выбора из истории сессий (команда `/resume`).

**Древовидное отображение**: через `<TreeSelect<LogTreeNode>>` разветвлённые сессии (fork) отображаются в виде дерева родитель-потомок, раскрытие/свёртывание управляется `expandedGroupSessionIds`.

**Три режима просмотра**: `viewMode` может быть `"list"` (список по умолчанию), `"search"` (поиск), `"preview"` (предпросмотр сессии).

**Нечёткий поиск Fuse.js**: использует нечёткое сопоставление с `FUSE_THRESHOLD = 0.3` в сочетании с `DATE_TIE_THRESHOLD_MS = 60 * 1000` (результаты в пределах 1 минуты сортируются по релевантности, иначе — по времени).

**Предпросмотр фрагментов результатов поиска**: `extractSnippet()` берёт по `SNIPPET_CONTEXT_CHARS = 50` символов до и после позиции совпадения, рендерит контекст с помощью `chalk.dim`, а совпавшее слово — с выделением (`LogSelector.tsx`).

**Константы глубокого поиска**:
```typescript
const DEEP_SEARCH_MAX_MESSAGES = 2000;
const DEEP_SEARCH_MAX_TEXT_LENGTH = 50000;
```
(В настоящее время `isDeepSearchEnabled = false` — ожидаемая функция)

**Оптимизация React Compiler**: `import { c as _c } from "react/compiler-runtime"` в начале файла указывает на компиляцию React Compiler; `_c(247)` выделяет кеш memo на 247 слотов, обширное условное мемоизирование предотвращает перерисовку поддеревьев.

## 12.7 Анализ архитектурных решений

### Почему кастомный рендерер Ink, а не оригинальный

Оригинальный Ink сериализует дерево React в строку и использует `log-update` для инкрементной записи — дизайн, ориентированный на простые CLI-инструменты. Требования Claude Code выходят за пределы этой модели:

1. **Выделение мышью**: требует отображения координат ячеек уровня экрана (hit-test); строковая модель это не поддерживает.
2. **Подсветка поиска**: требует наложения инвертированных ячеек на уже отрендеренный кадр; необходима работа с матрицей ячеек.
3. **Аппаратная прокрутка DECSTBM**: требует согласованности двух кадров (prev/next) в области прокрутки; строковый diff не может имитировать эффект аппаратной прокрутки терминала.
4. **Позиционирование курсора IME / a11y**: необходимо точно знать физические экранные координаты курсора ввода, чтобы разместить физический курсор терминала в правильной позиции (preedit-текст метода ввода CJK рендерится в позиции физического курсора).
5. **Атомарность Alt-screen (BSU/ESU)**: необходимо обернуть erase + paint в `\x1b[?2026h`/`\x1b[?2026l`, предотвращая рендеринг промежуточных состояний внешними терминалами типа tmux.

### Соображения о производительности двойной буферизации

Вывод в терминал является I/O-интенсивной операцией; системный вызов `write()` имеет фиксированные накладные расходы. Стратегия двойного буфера и diff снижает объём записи каждого кадра с O(размер экрана) до O(изменённая область). Комментарии с результатами измерений показывают: кадр только drain (только DECSTBM scroll, без commit React) генерирует ~10 patch и ~200 байт вывода (`ink.tsx:756`), тогда как полная перерисовка требует нескольких тысяч байт.

Флаг `prevFrameContaminated` является страховочной сетью корректности: когда операции наложения подсветки выделения, `resetFramesForAltScreen()`, `forceRedraw()` и другие изменяют содержимое frontFrame, следующий кадр должен делать полный diff, не полагаясь на инкрементную оптимизацию blit (`ink.tsx:743`).

### Мотивация реализации режима Vim

Основная аудитория пользователей Claude Code — опытные пользователи Vim; для них применение клавиш Vim в поле ввода — не украшение, а базовая потребность. Реализация на чистом конечном автомате (без зависимостей, без побочных эффектов) делает логику Vim полностью покрытой юнит-тестами и развязанной с уровнем рендеринга терминала.

Комментарий в начале `types.ts` раскрывает философию проектирования: **типы как документация**. Union type `CommandState` описывает конечный автомат точнее любого комментария — исчерпывающая проверка switch в TypeScript гарантирует обработку каждого состояния, а пропуск нового состояния вызовет ошибку компиляции (`types.ts:1`).

## 12.8 Переносимые паттерны

Следующие паттерны проектирования можно заимствовать в других терминальных приложениях или UI-фреймворках:

**1. Разделяемый Pool + Integer ID буфер экрана**
Хранить целочисленные ID символов/стилей в `Int32Array`, а не строки или объекты. Разделяемый между кадрами Pool сводит diff к сравнению целых чисел, полностью устраняя давление на GC. Применимо в любом сценарии с высокочастотным diff прямоугольной матрицы.

**2. Типы как конечный автомат**
Определять конечный автомат через TypeScript union type — каждое состояние несёт ровно нужные данные, а функция переходов использует exhaustive switch. Возвращаемое значение `transition()` + `TransitionResult` с двумя ключами `{next?, execute?}` крайне лаконично и может быть напрямую перенесено в другие сценарии обработки клавиш.

**3. Инкрементный diff на основе прямоугольника повреждений (Damage Rectangle)**
При рендеринге записывать реально записанную прямоугольную область (`damage`), diff сканирует только эту область. Применимо к любой системе кадрового буфера — не только терминалы; этот паттерн используется в игровом UI и встроенных дисплеях.

**4. Двойной буфер + страховочная сеть prevFrameContaminated**
Когда определённые операции не следуют нормальному пути рендеринга (прямое изменение переднего кадра), использовать булев флаг для принудительного полного diff следующего кадра, не нарушая инвариант двойного буфера. Эффективнее полной перерисовки каждого кадра и корректнее допущения грязных данных.

**5. Задержка рендеринга через microtask**
Паттерн `scheduleRender = throttle(() => queueMicrotask(onRender), 16)` гарантирует полную фиксацию layout-эффектов React до рендеринга, предотвращая однокадровое запаздывание позиции курсора. Также применим в других сценариях React + кастомный рендерер.

**6. Кеш ширины строк (специализированная оптимизация для потокового вывода)**
Вычисление `stringWidth` для большого числа неизменившихся строк при потоковом выводе является горячей точкой. Простая стратегия Map + очистка при заполнении в `line-width-cache.ts` решает ~50x снижение вычислительных затрат (в комментарии оригинала) за 20 строк кода и может быть напрямую перенесена в любой сценарий потокового рендеринга текста.
